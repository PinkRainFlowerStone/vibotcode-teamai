# Frontend Mini Program Profile

本画像为 `frontend-mini-program` 命名空间的通用平台基线。平台识别以应用清单、页面/分包配置、开发者工具配置、依赖、构建目标和用户明确说明为证据，不以仓库名判断。

## Scope

- 微信原生小程序：JavaScript/TypeScript、WXML、WXSS、JSON、原生组件和 `wx.*` API。微信官方约束可直接用于核对。
- 其他小程序或跨端构建：只复用平台中立的风险检查；生命周期、组件、API 和配置以目标平台及目标仓库为准。
- 普通 PC Web 和移动 Web 不使用本画像。

## Evidence Precedence

1. 微信官方文档、官方示例和目标基础库的实际行为定义不可绕过的平台约束。
2. 目标仓库的需求、配置、相邻实现和现有接口契约决定目录、架构与业务选择，但不得违反平台约束。
3. 社区通用工程实践用于补足安全、异步收口、状态归属、资源清理、可维护性和验证方法；这些实践不得伪装成微信官方强制规则，也不得覆盖明确的仓库契约。
4. 初始化模板和参考项目只用于发现可能存在的运行形态与风险面，不具有默认架构或团队业务规范效力。

## WeChat Official Baseline

### Configuration

- `app.json` 定义应用级页面、分包和能力配置；页面与组件 JSON 定义各自边界。配置必须与真实文件、调用和发布环境一致。
- 主包、分包、独立分包、预下载和懒加载是发布与启动策略，必须按当前官方限制、基础库和仓库结构判断，不在团队资源中固定易变化的数值。
- 开发者工具配置用于开发与上传，不代替运行时授权、域名、隐私和版本配置。

### Lifecycle, Rendering And Components

- `App`、`Page`、`Component` 使用各自生命周期；页面栈切换、隐藏、卸载和组件分离不是 Web 路由或 Vue 卸载的同义替代。
- 视图同步使用 `setData`。直接修改 `this.data` 不会可靠同步视图，并可能造成状态不一致；高频事件应减少更新次数和载荷。
- WXML 使用平台数据绑定、条件/列表渲染与事件；WXSS 的全局、页面、组件样式边界受实际样式隔离配置约束。
- 原生组件以 `properties`、事件、方法和生命周期形成契约；`observers`、`behaviors`、`relations` 只在确有关系模型时使用，并处理更新循环与销毁清理。

### Platform APIs And Trust Boundaries

- `wx.request`、上传、下载和 Socket 受平台网络配置与运行环境约束；请求应经过仓库现有网络、鉴权和错误链路。
- `wx.login` 产生临时登录凭证，由服务端完成身份交换。小程序端不得包含 `appSecret`、服务端密钥或最终授权逻辑。
- storage 不是秘密存储。敏感信息、个人信息和支付上下文必须有明确的必要性、生命周期与清理设计。
- 隐私、授权和敏感能力需要同时核对平台声明、用户同意/拒绝、失败降级和真实设备行为。
- 支付、订阅消息、分享、扫码、定位、媒体、文件系统等能力属于高风险集成，需明确客户端和服务端职责并验证重复触发、取消与失败路径。

### Optional WebView Shell Profile

部分业务小程序以原生页面提供登录、手机号、支付、定位、分享或跨小程序能力，以 `<web-view>` 承载主要 H5 业务。这只是原生页面、组件化应用、分包应用等多种实现形态中的一种，不是 `frontend-mini-program` 的默认或推荐架构。只有目标仓库自身的配置和代码确实采用此结构时才应用以下画像：

- 微信公众平台业务域名、服务器域名与仓库环境配置共同决定可访问边界。
- 页面入口 URL、H5 消息、分享链接和跨小程序路径属于跨运行时输入，需要允许范围、字段协议和编码层级。
- 临时登录凭证、业务 token 或授权码在原生、H5 和服务端之间的交接必须有明确的受信目标、用途、时效和清理策略。
- 原生页面栈、WebView 返回、H5 重定向及跨小程序返回需要显式协议和失败兜底，不依赖偶然页面状态。

2026-11-23 对 `mini-template` 的只读梳理仅佐证了这一可选项目形态，并暴露了可供检查的跨运行时风险面。该模板不决定默认架构、业务规则或实现方式，其中的页面、字段、域名、AppID、storage 键和未完成示例均不具有规范效力。

### Compatibility And Performance

- 依据仓库目标基础库判断 API/组件可用性；必要时使用 `wx.canIUse` 或现有兼容层，不以开发者工具单一环境替代版本判断。
- 重点检查 `setData` 传输、长列表、图片媒体、资源清理、主包与分包边界。性能结论需要真实测量或平台工具证据。
- 开发版、体验版、正式版的域名、权限、数据和 `envVersion` 可能不同，发布和回滚沿用仓库现有流程。

## Repository-Owned Decisions

以下内容没有业务仓库证据时保持仓库自定：目录布局、页面路径、业务字段、接口结构、组件库、状态方案、请求封装、storage 键、环境变量、最低基础库、包体积预算、命令、CI、预览/上传和验收入口。

TypeScript 是条件化能力：仅在仓库已采用时遵循其 `tsconfig`、类型声明和构建配置，不要求 JavaScript 项目迁移。

## Verification Contract

验证报告必须分别列出：实际运行的命令、开发者工具结果、预览/体验版或真机结果、未执行项和残余风险。静态 lint、类型检查、单元测试或组件模拟不能替代支付、隐私、授权、分享、定位、媒体、文件、Socket、性能和兼容性的真实运行环境验证。

当前 `mini-template` 初始化模板仅作为只读辅助样本，不能替代官方依据、社区通用工程实践或目标仓库证据，因此本画像不声明固定业务规则。官方来源、实践层级与样本快照记录在 `docs/vibotcode/resource-provenance.md`。
